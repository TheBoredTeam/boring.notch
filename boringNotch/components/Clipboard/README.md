# Clipboard History

A built-in clipboard history manager for **boring.notch**. It records what the user copies across apps — text, links, images, and files — and surfaces them as cards in a notch tab so they can be re-copied, opened, revealed, or deleted.

## Layout

```
Clipboard/
├── Models/
│   └── ClipboardItem.swift          # `ClipboardItem`, `ClipboardItemKind`, blob/file refs
├── Services/
│   ├── ClipboardMonitor.swift       # Polls `NSPasteboard.general`, captures new copies
│   ├── ClipboardActionService.swift # Re-copy, open link, reveal, copy path, delete, clear
│   └── ClipboardPersistenceService.swift  # JSON history + image blob storage on disk
├── ViewModels/
│   └── ClipboardStore.swift         # `@MainActor` store owning the history array + thumb cache
└── Views/
    └── ClipboardView.swift          # Tab panel + per-item card UI
```

## How it works

There is no change-notification API for the general pasteboard, so `ClipboardMonitor` polls `NSPasteboard.general.changeCount` every **0.5s** (the de-facto interval among macOS clipboard managers). When the count advances, the new payload is captured once, deduplicated, and inserted into `ClipboardStore`.

### Capture priority

`ClipboardMonitor.capture(from:)` resolves a copy into exactly one kind, in this order:

1. **Files** — file URLs win over everything. A Finder copy of an image carries both a file URL and image data, and the file reference is strictly more useful.
2. **Images** — PNG, then TIFF. A browser copy carries HTML alongside a PNG; the image is the better artifact.
3. **Links** — a bare string that parses as an `http`/`https` URL with a host and no whitespace.
4. **Text** — anything else.

Each branch **returns rather than falls through**, so a disabled type never degrades into a surprise capture of a lower-priority representation.

### Kinds

- **Text** — stored inline in the history JSON.
- **Link** — stored as a `URL`; the card shows host + path.
- **Image** — stored as a full-fidelity blob + a downscaled thumbnail under `Application Support/boringNotch/Clipboard/Blobs/`. Re-copy writes back the original representation, never a transcode. Capped at **20 MB**; over the cap the image is skipped rather than silently stored in part.
- **Files** — stored as `ClipboardFileRef`s with a best-effort security-scoped **bookmark** plus a plain `path`. The bookmark cannot always be minted from a pasteboard URL, so `path` is always present and keeps re-copy, reveal-in-Finder, and icon lookup working when the bookmark is `nil`.

### Deduplication

`ClipboardStore.insert` keys on `ClipboardItem.identityKey` (payload-derived, with a SHA256 `contentHash` for images so dedup never re-reads blobs). Re-copying an existing entry **moves it to the front and refreshes its timestamp** rather than being skipped or creating a duplicate. Image dedup reuses the stored blob instead of writing a new file only to delete it again.

## Persistence

`ClipboardPersistenceService` writes the history to a single compact JSON file (`history.json`) under `Application Support/boringNotch/Clipboard/`. Writes are **debounced (0.75s) and run on a background queue** — clipboard capture is a far hotter path than Shelf drops, so blocking the main thread on every copy is not acceptable. `flush()` is called from `applicationWillTerminate` so the last debounce window isn't lost on quit.

Loading is defensive: if the whole-array decode fails (e.g. a truncated write from a crash), it salvages whatever individual entries still parse rather than discarding the entire history.

Image blobs live in a sibling `Blobs/` directory. Only **file names** are persisted, never absolute paths — the sandbox container path embeds the bundle identifier, so absolute paths wouldn't survive a container move. Orphaned blobs are reclaimed by `garbageCollect` at launch and on `clearAll`.

## Settings

All toggles live in `Defaults` and are read live by the monitor and store:

- `clipboardHistoryEnabled` — master switch; starts/stops the poll timer.
- `clipboardHistoryLimit` — max entries; lowering it trims immediately.
- `clipboardCaptureFiles` / `clipboardCaptureImages` / `clipboardCaptureLinks` / `clipboardCaptureText` — per-kind capture toggles.
- `clipboardIgnoreConcealed` — skip payloads marked `org.nspasteboard.ConcealedType` (password managers, etc.).

### Always-honored privacy markers

Regardless of settings, copies tagged with any of these pasteboard types are never recorded:

- `org.nspasteboard.TransientType`
- `org.nspasteboard.AutoGeneratedType`
- `de.petermaurer.TransientPasteboardType`
- `com.typeit4me.clipping`
- `Pasteboard generator type`

## Actions

`ClipboardActionService` mirrors the static-namespace shape of `ShelfActionService`:

- **Copy** — puts an entry back on the pasteboard. Routed through `ClipboardMonitor.performOwnWrite`, which stamps a source marker and samples `changeCount` so our own writes don't come back as fresh captures.
- **Copy Path** (files) — writes newline-joined paths as text.
- **Open Link** (links) — hands the URL to `NSWorkspace`.
- **Reveal in Finder** (files) — works with or without a resolvable bookmark; revealing is an app-to-app request, not a file read.
- **Delete** / **Clear All** — remove from the store, evict the thumbnail, and delete the blob files.

For file copies, security-scoped URLs are held open for the lifetime of the paste (`copiedURLs`) so the receiving app can still resolve them when the user pastes; they are released on the next copy.

## Design notes

- `ClipboardItem` is deliberately **not** `@MainActor` (unlike `ShelfItem`). Keeping it actor-agnostic and `Sendable` is what lets `ClipboardPersistenceService` encode and write on a background queue.
- `ClipboardStore` is newest-first (unlike `ShelfStateViewModel`, which appends).
- `ClipboardThumbnailCache` is an `actor` mirroring `ThumbnailService`'s coalescing so a fast scroll can't kick off duplicate loads for the same item.
- The card's **Copy** action deliberately does **not** reorder the list — move-to-front would make alternating pastes of two entries shuffle under the cursor.
- Clear-all uses a two-stage inline confirm (a `.confirmationDialog` would be orphaned — the notch closes on mouse-exit and would strand the dialog).
